# Design system

## Product brief

We design for a developer who enjoys going to the gym and wants a minimal workout tracker: fast editing, a clear overview, visible progress and a reason to keep coming back. This direction comes from the product owner; it is a design brief, not findings from user research.

The product promise is: **Log quickly. See where you stand. Notice your progress.**

Developer familiarity should inform our respect for efficiency and precision. It does not justify technical language, configuration-heavy screens or requiring keyboard shortcuts to complete an action.

### Core user needs

- Before training: understand recent workouts and quickly start or repeat a session.
- During training: see the current exercise and set, enter weight and repetitions, and correct mistakes with little effort.
- After training: review what was actually completed and understand the session at a glance.
- Over time: see personal progress and feel encouraged to return.

### Design principles

| Principle                          | Design consequence                                                                                                                                                      |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Minimal, but understandable        | Keep the next action prominent. Use clear labels and progressive disclosure rather than hiding essential actions behind unfamiliar icons.                               |
| Fast to edit, safe to correct      | Keep frequent edits close to their values. Distinguish editing a value from logging a set, preserve input on failure and make recovery clear.                           |
| Confirm before deleting            | Every delete, removal or discard action opens a confirmation modal before changing data. Name what will be lost, explain permanence, and provide a clear Cancel action. |
| An overview before detail          | Lead with information needed for the current task. Keep workout summaries scannable and exercise and set details easy to reach.                                         |
| Progress grounded in real training | Explain metrics, units and comparison periods. Distinguish completed work from planned work, and handle limited history honestly.                                       |
| Motivation without pressure        | Make completed work and personal improvements visible. Use calm, specific encouragement; avoid guilt, invented achievements or rewards that distract from training.     |

### Design review questions

Can the user identify the next action at a glance? Can they change a value and recover from a mistake without losing context? Can they distinguish planned, edited and logged values? Does the overview explain what they did, and does progress show a meaningful comparison? Does the experience encourage returning after a break?

These principles guide future work; they do not claim every behavior is already implemented. Phone use between sets, one-handed interaction and short attention windows are working assumptions to validate. Exact progress comparisons and motivational feedback still need design decisions. A developer audience does not by itself establish demand for gamification, social features or advanced analytics.

The Histoire **00 Start here / Product brief** page presents this direction alongside the component catalog. Responsive specifications, a complete typography scale and workflow coverage remain separate documentation work.

## Visual foundation

The Workout Tracker adopts the visual identity of the [Vue PWA starter](prior-art.md#vue-pwa-starter-look-2026-10-10): a warm light theme by default, a dark theme, a choice of five accent colors, Geist and rounded 8px controls. The owner chose this identity on 2026-10-10, replacing the earlier dark-only, single purple accent, Inter design. See [the decision record](history/visual-identity-2026-10-10.md).

Values live in [`packages/ui/src/tokens.css`](../packages/ui/src/tokens.css). Each color is one `light-dark()` pair, so a theme change needs no second stylesheet. [`packages/ui/src/workout-theme.css`](../packages/ui/src/workout-theme.css) maps these roles to the shared component roles (`--ui-*`). App layout lives in [`apps/workout/src/style.css`](../apps/workout/src/style.css).

### Theme and accent

The Settings **Appearance** page has a Theme choice (System, Light, Dark) and an Accent choice. Both are radio groups with 44px targets and visible labels. The choice stays on the device in `localStorage` (`workout-theme`, `workout-accent`); System is the default and follows the device, including while the app is open. [`app/appearance.ts`](../apps/workout/src/app/appearance.ts) owns the choice. It sets `data-theme` (resolved to `light` or `dark`) and `data-accent` on `<html>` before the app mounts, and updates the `theme-color` meta tags to the resolved background. An inline script in `index.html` and `preview.html` sets both attributes before first paint, so a saved dark theme does not flash light. Without script or storage the document follows `prefers-color-scheme`, in blue.

The web manifest has one `theme_color` and `background_color` (light). An installed app that follows a dark system theme therefore shows the light splash screen. The iOS status bar style is `default`, because a translucent bar with light text would be unreadable on the light theme.

### Type, shape and navigation

Geist Variable is bundled by `@form/ui/styles.css`, which makes the package self-contained, and works offline. Headings use weight 600 with tight tracking; eyebrows, section labels and the active workout label use the system monospace font in small capitals. Controls are 44px high with an 8px radius; cards use an 8px radius and a hairline border; sheets round their top corners at 16px. The focus indicator is a 3px accent ring at 65% opacity with a 3px offset on every focusable control.

On desktop the sidebar marks the current page with an inverted pill (text color on the background color). On phones the persistent four-item bottom menu keeps its labels, marks the current page with a short bar above its icon and a heavier stroke, and uses a translucent, blurred background. Lucide icons use a consistent light stroke. Mobile uses large number inputs and a compact rest timer. Phones show one large page title per screen: the workspace topbar appears only to report offline status. On desktop the topbar breadcrumb sits above every screen except the training session, and Workouts, Exercises, Progress and Settings (with its detail screens) share one centred content column of `--page-column` (760px), so their titles start at the same x and y. Lists are `BaseListGroup` cards of `BaseListRow` rows with one `--rule` hairline between rows and 52px artwork; touch screens keep no hover tint after a tap. Dialogs use Reka focus trapping and explicitly return focus to their opener.

The interface uses a quiet visual hierarchy; empty states show actual data rather than fabricated statistics. [Prior art](prior-art.md) records the original reference and adaptations. Exercise artwork is dark charcoal with transparent backgrounds; check it on both themes when it changes.

## Mobile motion and feedback

Motion explains a change without delaying the next action. Shared motion tokens define a 120ms press response, 180ms exit, 240ms entrance and 280ms completion response. Mobile sheets and numeric editors slide from the bottom; desktop dialogs use a small scale and fade. Close, Escape and backdrop dismissal retain the existing confirmation and focus contracts. On phones, `BaseSheet` shows a grabber; dragging its header follows the finger, and a long pull or quick flick dismisses through the same path as Escape, so dirty editors still ask before discarding. A short drag springs back. Reduced motion removes the follow and spring animations.

Buttons compress subtly on press without changing layout. Completion feedback runs only when a mounted control changes from incomplete to confirmed complete, never for an initial saved value or numeric draft confirmation. Reduced motion removes movement, including sheet and dialog state animations; the final state remains visible.

Startup shows a lightweight branded loading surface with no minimum wait. The exercise library appears immediately when its data is ready, without an entrance fade delaying readable catalog content. Installation allows browser-managed promotion alongside a user-invoked sheet with platform-specific instructions and native installation when available. The app checks for a new deployment hourly and whenever it returns to the foreground. It shows an Update app notice outside an active workout and reloads a tab only when that tab's user chooses it. When the update is accepted in another tab, this tab keeps running and shows an "Updated — reload when ready." notice with a Reload app button, also outside an active workout; it never reloads on its own. There is no onboarding or guided tour. Develop shared components and review their Histoire examples before integrating application behavior.

### Status and feedback

Every message is a `BaseNotice`: `danger` for failures (role alert), `success` for a finished action and `info` for guidance, with any buttons in the action slot as `BaseButton` variants. A sheet or page failure is a danger notice inside that sheet or page; `BaseFieldError` stays on the field it describes (the set row's weight and repetitions). Whole-page and in-list empty states are `BaseEmptyState` (`panel` for a page or section, `compact` inside a list). A page-level failure that replaces the screen uses the `h1` level and takes focus.

One event produces one visible message:

- Logging a set shows only the training notice ("Back squat · set 1 logged."), a `BaseNotice` that floats above the dock as a toast (bottom right on desktop). It takes no layout space, so neither the set rows nor Discard workout move when it appears and no gap is left when it is absent, and it carries no controls, so taps pass through it. It ends after eight seconds, like the footer line. The exercise strip and the set row carry the persistent logged state, so there is no separate "Set logged" line.
- The footer line ("Saved on this device", "Workout saved. Another session in the books.") is ambient feedback for work done outside a session. It disappears after eight seconds and when the route changes. It is hidden during an active workout, where the training notice and the desktop rest panel's save state already say it.
- Finish posts "Workout saved" for Workouts Home. It is announced there and gone after navigating away.
- Settings pages show the result of Export, Import and Delete in a notice under the action: success for a completed action, danger for a failure, info when the data changed and the action did not run.
- The offline, Update app, "Updated — reload when ready." and name-recovery notices stay until the user acts or the condition ends. The floating ones (name recovery, input recovery) only position a `BaseNotice`; they keep their `aside` label and remain reachable above the bottom navigation.

## Button ownership

Icon-only actions use the shared `BaseButtonIcon`: a required accessible label, decorative icon, centered content and a minimum 44px square touch target at every viewport size. Circle and square surfaces share this geometry. Application classes position these controls without resetting their internals.

Every button keeps the UI package's variant and size styling. `BaseButton unstyled` is not allowed in the app: lint rejects it, and a new button shape becomes a variant, a size or a shared component instead of an app class. Text actions are `variant="link" size="sm"` (accent) or `variant="ghost"` (neutral). A left-aligned, wrapping button as tall as its content (the dock's two-line Next target, the sidebar entries, the draft-conflict choices) is `size="row"`. Cards and rows are `BaseListRow as="button"`; selectable chips are `BaseChoiceChip`; the exercise strip tab is `BaseMediaTab`; calendar days are `BaseDayCell`. The set row's number and log buttons are `BaseButtonIcon` (`secondary`, or `default` while the set is the one to log); the application class only adds the logged tint and the draft border. Global resets must exclude shared buttons; removing their flex layout is what previously displaced the settings icon. Histoire's BaseButtonIcon story owns the isolated interaction examples.

The desktop sidebar installation action uses a left-aligned label with an icon column. Wrapped labels stay aligned with their first line; the local-storage note uses the same icon and label offsets.

## Settings navigation

Settings is a full page at `/settings`, reached through the content footer on desktop and through a gear icon with a Settings label in the mobile bottom navigation. At the phone breakpoint (650px) the content footer hides its Settings link because the bottom navigation already has it, and it keeps only the save line. During an active workout on phones the training dock replaces the bottom navigation, so Settings is not offered there. The bottom navigation has four equally sized destinations: Workouts, Exercises, Progress, and Settings. Its Settings link uses the same selected styling and active-page announcement as the other destinations. During an active workout, the training dock replaces the mobile bottom navigation. On wider screens the content footer uses a native navigation link with a visible focus outline and a minimum 44px touch target. The current Settings link announces its active page. Settings has no header or sidebar trigger and does not open an overlay. Desktop navigation keeps its three destinations.

Settings is an iOS-style hub with detail pages, the structure of the [Vue PWA starter](prior-art.md#vue-pwa-starter-look-2026-10-10). The hub at `/settings` shows the large Settings title (a root `BasePageHeader`), an app card (name, tagline and an Offline ready or Preparing badge) and rows in groups. A row has a colored icon tile, a title, the current value on the right and a chevron, and is at least 56px high. Every group has a label: **General** (Training preferences, Appearance and Language; German "Allgemein"), **This device** (Install app) and **Your data** (Export backup, Import backup, Delete all data). Tile tones follow what a row is: the accent tile is for the General rows, which change how the app trains or looks; the muted tile is for device and data housekeeping (Install, Export, Import); the danger tile is for deletion. A privacy line closes the hub. The row titles and values are the current choice, for example "Auto rest · 90 sec", "System · Blue" and "Deutsch", so most questions are answered without opening a page. `BaseListGroup` and `BaseListRow` in `@form/ui` draw the groups and rows.

Each row opens `/settings/<section>` with `section` one of `training`, `appearance`, `language`, `install`, `export`, `import` and `delete`. A detail page starts with a pinned bar (`BasePageHeader`): a ‹ Settings back link on the left and the page title as the page heading. The bar stays at the top while the content scrolls; on phones it also covers the device safe area. Content is one column of at most 560px, centered on wide screens.

- **Training preferences** has the automatic rest timer switch, the rest duration select and the weight unit, in one group of rows.
- **Appearance** has a Theme segmented control (System, Light, Dark; `BaseSegmentedControl`) and the accent color picker with five swatches. **Language** has a segmented control for System, English and Deutsch and reports a catalog that failed to load.
- **Install app** shows the home-screen and offline state and the Install app action, which is disabled once installed.
- **Export backup** and **Import backup** each explain their action, then offer one button and an always present status line. Import shows the chosen file name, the merge rules, Cancel import and Import this backup.
- **Delete all data** explains the deletion and has one neutral button. The confirmation contract for [destructive actions](#destructive-actions) is unchanged. The sheet names history, the active workout, drafts, templates, custom exercises and the preference reset, and downloaded backups remain on the device.

Focus follows the navigation. Opening a page moves focus to its heading, without scrolling and without a visible ring. Back, by the link or the browser button, returns focus to the row that opened the page. Choosing the Settings tab or footer link from a page returns to the hub and leaves focus where the shell puts it. The Settings tab stays selected on every Settings page. An unknown `/settings/<section>` address opens Workouts like any unknown path. Browser Back returns to the previous page. Leaving the Import page clears an unsubmitted backup selection. While a backup runs, Delete all data waits. Saved preferences and workout drafts remain in the shared workspace.

Deliberate differences from the starter: the workout app has no persistent brand header, so only the detail bar is pinned; the tiles use the accent, muted and danger tones because the palette has no status colors; and Appearance has no live preview card.

## Durations

One formatter shows how long a workout took: `format.duration(ms)` from `useFormat()`. It rounds to whole minutes, never below one, and uses `Intl.NumberFormat` short units, so the unit and its plural follow the language: "24 min", "1 hr 5 min" and "2 hr" in English, "24 Min." and "1 Std. 5 Min." in German. A 24-second workout reads "1 min" on Finish and in History alike. `format.durationParts(ms)` splits the same value into a number and a unit for `BaseStat`. Finish, the completed-workout review, Home, History and the calendar list all use it. Two things stay `mm:ss` clocks on purpose because they count live: the elapsed time under the session header and the rest countdown (`clockTime` in `ui/presentation.ts`).

## Destructive actions

Deleting data, removing exercises or sets, clearing a logged result, discarding input drafts, and reducing a template or workout set count require an additional confirmation modal. The initiating control never performs the deletion. State the affected data and consequence, label the confirming action explicitly, and make cancellation easy. Escape, the close button and backdrop dismissal cancel. Keep initial focus on a safe control and restore focus on dismissal. Disable repeated submission while saving and report failures without claiming success. A conflict requires another review before deletion.

Every confirmation is a `BaseConfirmSheet`. Deleting, removing, discarding, clearing and reducing a set count use `intent="destructive"` (the destructive button, Cancel or Keep editing on the left and focused first); finishing a workout is `neutral` with a "Save workout" confirm. Use the existing palette and modal surfaces; deletion does not introduce a new warning color. Undo logging is an explicitly named set-options action. Cancelling an unconfirmed numeric edit or changing a picker selection does not delete saved data.

## Workout-first screens

Workouts Home summarizes the latest workout and links to full history and templates. A fresh journal has one prominent start action. The exercise picker supports search, filters, and multiple selection. New workouts open this picker before a session exists. Its fixed Start (count) action creates the selected workout; cancelling returns to Home without starting the clock. During training the same picker uses Add (count). Saving prevents dismissal, and errors retain selection. The active workout presents a horizontally scrollable thumbnail strip and one selected exercise. Native navigation buttons announce exercise names, selection and completion. The saved exercise order stays stable, including after the last set is logged. Before the first logged set, the header shows only the exercise count. Logging reveals set progress and volume. The picker remains available during training and after all sets are logged.

The compact workout header shows the saved title and a Rename workout action. Rename opens a sheet. Workout name changes use Save name or Enter. Moving focus to another control does not save the name or swallow the next action. Unsaved name input stays in the rename sheet and must be saved or cancelled before finishing. Conflicting names show explicit Keep my name and Use saved name choices.

The session omits the duplicate workspace topbar while retaining offline status. Its header is the pinned detail `BasePageHeader`: a ‹ Workouts `BaseBackLink` (accessible name "Back to workouts"), the workout name as the page heading, and Finish in the action slot (an accent text action on phones, muted while unavailable). Below the bar, in the page, sit the elapsed time with the Rename workout button, the set count and the progress line; the rename button is not in the bar because the name needs the room. A long name shows two lines in the bar. Like every detail header it takes focus when the session opens; Back returns focus to the main region of Workouts. History keeps its focus contract: the browser focuses the main region after the view changes. Discard workout is a quiet centred action below the exercise; the training dock carries only rest and next-set controls. The selected exercise shows its name in the text color (the accent is for selection and actions, never for headings), equipment, repetition prescription and optional note. Rounded set rows align set number, weight, repetitions and an explicit log button. Numeric confirmation updates the draft only. The action logs unfinished sets or saves corrections to logged sets. Unchanged logged rows show a non-mutating Logged state: a tinted button with an accent check, whose name says Logged. The current unlogged row offers earlier values in a tinted bar on the set grid below it, with a notch under its set number: a source icon (repeat for the previous set, history for last time), weight under kg and repetitions under Reps. Tapping the values fills the input and moves focus to the log button; the check under Log fills and logs in one tap. Logging the last unlogged set opens the Finish sheet. Set options expose Undo logging explicitly. The row options open a detailed editor with save-without-logging, explicit clear and discard-input actions. Inline rows are unmounted while that editor is open to avoid duplicate control IDs. Closing returns focus to the corresponding row, with the selected exercise or add control as a fallback.

The exercise ellipsis opens grouped options for targets, set editing, notes, replacement and removal. Draft recovery and conflict choices remain visible with the affected row. Saved rest deadlines drive the compact mobile dock, with skip or dismiss controls. Rest uses the user's configured duration; corrections do not restart it. Controls retain at least 44px touch targets at narrow widths. The current row uses accent emphasis; logged rows retain a quiet accent check. A Last time card below the rows shows logged sets from the most recent completed workout containing this catalog exercise, combining repeated entries and preserving zero-repetition attempts. It is absent when no matching logged history exists. Review presents results, the exercise ledger, then one equal-size `BaseActions` footer: Edit workout and Save as template are secondary and Repeat workout is the primary action, last. The accent applies to selection and logged work; there are no unsupported metrics or invented history.

For a fresh journal, the welcome card owns the only start action. Its copy wraps naturally and its height follows its content. Mobile uses a compact mark and a full-width action; the page header omits repeated introductory copy. Returning journals without an active workout show one start action below their training rhythm. An active workout instead has one outlined card with its name, exercise and logged-set counts, and a single Continue workout action. The mobile navigation divides the available width equally among its rendered links, without unused columns.

Closing an exercise panel preserves its numeric input drafts. Changed notes, configuration and workout names ask before route navigation discards input, including browser Back. Changed templates ask before Cancel, Escape, close-button, backdrop dismissal or browser Back; unchanged editors close directly. Numeric editors accept a complete pasted value, accept a decimal comma or point alike, show the active language's decimal mark (a comma in German) while storing numbers, and reject invalid or overly precise input without replacing the current draft. Pasting does not confirm or log the value. Weight displays preserve up to two decimal places. The numeric editor uses a picker layout modelled on Strong: Cancel and the title on top, a scrolling column of values, then a row with an optional aside, the draft and an accent Done button above the keypad. The matching value in the list uses the shared selected tokens. On phones it fills the screen. Barbell weights show a plate diagram in the aside, coloured by the competition plate code (`--ui-plate-*` tokens), with an accessible description such as "Per side: 20 kg, 10 kg on a 20 kg bar". Training preferences list the bar weight and a `BaseChoiceChip` toggle for each plate size. A numeric trigger's accessible name combines its field label and visible value, for example “Set 1 weight for Bench press: 70.25 kg”, so voice control can target the number shown (WCAG 2.5.3, Label in Name).

Opening a workout selects pending input after recovery, or unfinished work when no input is pending. Review my sets selects, scrolls to and focuses the first pending row, even in another exercise. Finishing requires pending edits to be resolved. Draft feedback distinguishes retained input from applied values. The finish dialog names the exercises with pending input and makes clear that applying values does not log sets. Converting a workout to a template opens an editor so the user can remove skipped sets and adjust targets before saving. Domain meanings belong in [context](context.md).

Add set appears below the selected exercise's rows and selects the new row after a successful save. The dock's next-set action selects and reveals the first unfinished set without logging it or automatically advancing after completion. Configuration shows a visible Number of sets label. Numeric editors keep their confirmation action visible on short phones, with independently scrolling content. Narrow-screen buttons retain a minimum 44px height regardless of pointer type.

Completed-workout review offers Edit workout alongside repeat and template actions. The editor changes the workout name and recorded numbers for logged sets. Unlogged work remains read-only. Save applies the correction atomically and returns to review; Cancel does not change saved data. Dirty dismissal asks before discarding. Browser Back waits while a numeric keypad is open so unconfirmed input is not lost. Conflicts and save errors keep local input visible, with an explicit action to reload saved values. Editing does not reopen the workout or change its dates.

### Training rhythm dashboard

Workouts Home puts the title and, in the header's action slot, the calendar button in one row above the past seven local dates ending today. Each date shows its weekday, day number and a circular accent mark when it contains completed workouts. The outline identifies today. Empty dates remain visible without invented sessions.

Home contains one Start action or a compact active-workout card with Continue, then two list groups with the same container treatment: Latest workout (a row with the workout name, then its date and the inline summary "24 min · 3 sets · 800 kg"; the group's action slot holds View history) and Templates (one row with a count and a chevron). Standard fresh, returning and active states fit a 375 × 667 viewport above the fixed navigation. Larger text, long names and notices may scroll naturally; content is never clipped to enforce the compact layout. On phones the content footer's Settings link is omitted everywhere (see [Settings navigation](#settings-navigation)); save status remains announced.

The calendar button opens a monthly sheet; tapping a rhythm date opens its month with that date selected and focused. The month starts Monday. Future dates and next-month navigation beyond the current month are disabled. A selected date lists every completed workout from that date as one list group of review rows (name, then the inline summary). Selecting a workout closes the calendar before opening its existing review, which offers editing, Repeat workout and Save as template. Closing the review returns focus to the calendar action. Date controls have native button semantics, full date and workout-count labels, and at least 44px targets. Narrow grids scroll within their own container.

History is a separate view, searchable by workout name, exercise name or muscle group, with a pinned detail header: a ‹ Workouts back link (accessible name "Back to workouts") and the History title. It shows one list group of review rows (the same `SessionRow` as Home and the calendar) with date, inline summary and exercise names; the review owns editing, repeat and save-template actions. Templates opens a sheet. Browsing and editing share the existing template sheet, with focus moving to the name field on edit and back to the template action on save or cancel. Browser Back preserves a dirty editor and asks before discarding. The shell retains offline status.

## Product design workspace

[Histoire stories](../apps/design-system/src/stories) form the living product design workspace. **04 Pages** is the entry point for reviewing complete implemented screens; **05 Flows** connects screens into real workout journeys. **00 Start here**, **01 Foundations**, **02 Components** and **03 Patterns** provide context and reusable details. **06 Explorations** holds clearly labeled proposals, separate from implemented behavior. Flows start from a useful prerequisite and let designers perform the real actions. They must not pre-seed the advertised outcome or replace production transitions with story-only feedback. Explain what a component means and when to use it before implementation names or token values. Document Usage, Variants, States, Behavior, and Examples and limitations. Show real keyboard and focus behavior. Pattern stories use isolated local state and must not imply real persistence. Spacing examples are reference values, not additional global tokens. The [UI package guide](../packages/ui/README.md) owns detailed component API contracts.

### Selected state

`--ui-selected-bg`, `--ui-selected-border` and `--ui-selected-text` (in [`tokens.css`](../packages/ui/src/tokens.css)) resolve to `--accent-soft`, `--accent` and `--accent`. They are declared on `:root` and on `[data-accent]`, so a subtree with its own accent resolves them from it. Every selected surface reads these tokens, never `--accent` or a grey directly:

- `BaseChoiceChip` (toggle or radio, `compact` or `card`; the card also shows a check): plate sizes in Training preferences and the equipment and muscle-group cards in the exercise filters.
- The calendar day (`BaseDayCell`). Today is separate: a neutral outline and an underlined bold number, so today and the selected day differ even when they are the same date.
- The picker row (tinted row, border and circle check), the active workout's exercise tab (`BaseMediaTab`) and the matching value in the numeric editor's list.
- The accent swatch ring in Appearance (`BaseColorSwatch`). The swatch fill shows the colour itself.

Two controls keep their own idiom on purpose: the segmented control draws its selected segment as a raised surface, and `BaseSwitch` shows on/off with its track and thumb.

The check glyph means one thing in the session: log this set. The numeric editor's confirm button is a filled accent "Done" (German "Fertig"), with the accessible name "Done: weight", so confirming a draft never looks like logging a set.

These rules are the contract the lint enforces: native controls, `BaseButton unstyled` and the legacy classes are blocking errors in the app, and literal lengths fail the design ratchet, whose baseline is empty (see [Design ratchet](#design-ratchet)).

## Enforced token policy

Literal CSS colors belong in `packages/ui/src/tokens.css`, including generic overlay and shadow colors. All other CSS files and Vue style blocks use semantic variables; raw hex values, color functions, and named colors are rejected. Vue class bindings reject literal Tailwind palette classes and raw color values in class/style/fill/stroke/color attributes. Dynamic values assembled outside these expressions still require review; these checks are not a CSS data-flow analyzer. Status colors receive no palette exception. CSS imports also follow the workspace dependency policy.

`pnpm lint:vue` (also included in `pnpm verify` and the pre-commit hook) enforces the policy across both applications and the UI package:

- `@shadcn/lint` rejects raw Tailwind colors and arbitrary Tailwind values in supported Vue class expressions and TypeScript class helpers. Use named utilities or existing CSS variables, such as `bg-(--ui-primary)`, instead of `bg-red-500` or `rounded-[13px]`.
- `design/token-references` rejects unknown static `var(--name)` references and Tailwind variable shorthand in CSS declarations, Vue attributes and script strings, and TypeScript strings. Shared names come directly from the UI package's token and component stylesheets; stylesheet-local declarations are also accepted. For example, `var(--ui-primray)` fails instead of silently losing its color.
- The existing CSS rules continue to reject literal colors outside the token source, including Vue style blocks. A CSS variable does not exempt its raw color definition from that rule.

### Design ratchet

Two kinds of design rule run in `pnpm verify`:

- **Blocking rules** in `eslint.config.mjs` (`pnpm lint:vue`), for `apps/workout/src/**/*.vue`. `packages/ui` implements the primitives and is exempt. Each started in the ratchet and moved here when its count reached zero.
  - `native-controls` (`vue/no-restricted-html-elements`): a native `<button>`, `<input>`, `<select>` or `<textarea>`. Use a `Base*` component; wrap a native control that is the right primitive (the accent swatch radio, the file input, the checkbox) in a `@form/ui` component.
  - `legacy-classes` (`vue/no-restricted-class`): the classes `btn`, `text-button`, `notice`, `empty-state` and `field-error`.
  - `unstyled` (`vue/no-restricted-static-attribute` and `vue/no-restricted-v-bind`): `unstyled` on `BaseButton`, static or bound. Add a variant, a size or a shared component instead.
- **The ratchet** for `scales`. Its baseline is empty: the repository has no literal lengths left, and because `tooling/lint/ratchet.mjs` rejects new entries, every new violation fails. `pnpm lint:design` (part of `pnpm lint`) runs [`tooling/lint/design-ratchet.mjs`](../tooling/lint/design-ratchet.mjs), which counts violations per file and compares them with [`tooling/lint/design-baseline.json`](../tooling/lint/design-baseline.json). Keys are `file::rule`. A file without an entry may have none.
  - `scales`: a literal `px`, `rem` or `em` length in `font-size`, `border-radius` (and longhands), `gap`, `padding*` or `margin*`, in any stylesheet or Vue style block except `packages/ui/src/tokens.css`. Allowed: `0`, `auto`, percentages, `inherit`/`initial`/`unset`, the `1px` hairline, and anything inside `var()` or `env()`. Use the type, radius and spacing tokens above. Literals inside `calc()` or `clamp()` count, so write `calc(var(--space-2) * 3)` rather than `calc(var(--space-2) + 2px)`.

A count above its baseline fails and lists the lines. A count below it also fails, so the headroom cannot be reused: run `node tooling/lint/design-ratchet.mjs --update` and commit the lower numbers. `--update` only lowers entries and removes those that reach 0; it never adds or raises one, and `tooling/lint/ratchet.mjs` rejects a raised or new entry in the pre-commit hook and CI. The ratchet rules live in `tooling/lint/design-ratchet.config.mjs`, separate from `eslint.config.mjs`, because they would otherwise fail the blocking run. When a baseline reaches zero for a rule, move that rule into `eslint.config.mjs`.

The root `components.json` points the Tailwind linter at the workout stylesheet and UI source directory. It is lint discovery configuration, not a second palette. Histoire continues to consume the same shared CSS tokens.

The article's `no-restyle` and `no-unknown-classes` rules are not enabled: the app still owns CSS classes for layout and positioning, and the explorer has separately loaded CSS classes. These need component-specific contracts and stylesheet discovery before those rules can be applied without false positives. Named CSS classes and inline dimensions are not restricted by the Tailwind arbitrary-value rule. Type, radius and spacing are covered by the scales above instead; the Tailwind arbitrary-value rule does not check them. Static reference checks do not resolve dynamic variable names, CSS scope or runtime values; new tokens and local aliases still need design review.
